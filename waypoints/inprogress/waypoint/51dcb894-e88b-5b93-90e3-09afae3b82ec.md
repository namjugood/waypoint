# Waypoint 조회 스킬

이 스킬은 새로운 걸 만들지 않는다. `waypoints/INDEX.md`(태그트리)와
`waypoints/tags/` 아래에 이미 쌓인 기록을 읽어서, 사용자의 질문에 맞게
가공해서 보여주는 **하나의 조회 엔진**이다. 아래 프리셋들은 전부 같은
엔진 위에서 "어떤 질문을 던지느냐"만 다르다.

## 공통 절차

1. `waypoints/INDEX.md`를 읽어서 현재 프로젝트(현재 작업 디렉토리의 git
   remote 이름 또는 폴더명) 섹션을 찾는다.
2. 사용자 요청과 관련된 태그를 찾아, 필요한 만큼만
   `waypoints/tags/<project>/<tag>/*.md` 파일을 읽는다 (전부 다 읽지 말고
   관련 있어 보이는 것만 — 파일이 많으면 최신순으로 우선).
3. 아래 프리셋 중 어떤 것에 해당하는 요청인지 판단해서 그 형식으로 답한다.
   프리셋에 안 맞으면 그냥 자유롭게 관련 기록을 찾아 답해도 된다.

## 프리셋

### `/waypoint` 또는 "지금까지 뭐 했어" → 브리핑
현재 프로젝트의 최근 태그들을 훑어서 "지금까지 이 프로젝트에서 다룬 주제
목록 + 진행 상태"를 짧게 브리핑한다. 미완료(진행중/보류) 항목을 먼저,
완료 항목은 나중에 간단히.

### `/waypoint adr` 또는 "의사결정 기록 만들어줘" → ADR 생성
"여러 접근법 중 무엇을 택했고 왜 택했는지"가 담긴 waypoint 파일들을 찾아서,
표준 ADR(Architecture Decision Record) 포맷으로 정리한다:

```md
# ADR-XXX: <제목>
## 상태
<진행중/완료/보류>
## 맥락
<왜 이 결정이 필요했는지>
## 결정
<무엇을 선택했는지>
## 고려했지만 선택 안 한 대안
<has_unexplored_alt가 true인 항목의 unexplored_summary 활용>
## 결과
<지금까지 알려진 결과나 영향>
```

사용자가 원하면 이 내용을 실제 `.md` 파일(또는 docx/html — 이미 있는
docx/pptx 스킬 활용)로 저장해도 된다.

### "비슷한 거 있었어?" / "이거 예전에 겪지 않았어?" → 데자뷰 감지
지금 사용자가 겪고 있는 문제/질문의 키워드로 `waypoints/tags/` 전체
(현재 프로젝트뿐 아니라 다른 프로젝트도)를 훑어서, 비슷한 태그나 내용의
과거 기록이 있으면 알려준다. 있으면 "예전에 <프로젝트>에서 비슷한 걸
겪었고 이렇게 해결했다"는 식으로 요약. 없으면 없다고 솔직히 말한다
(억지로 끼워 맞추지 않는다).

### "반복되는 패턴 있어?" → 템플릿 후보 추출
여러 waypoint에 걸쳐 비슷한 요청 패턴(예: "테스트 코드 짜줘"가 자주

## 정리

**원인 진단**: 이전 세션에서 Archive를 눌렀지만 `waypoints/`에 아무것도 안 쌓인 이유는, 원문 대화 기록이 `SessionEnd` 훅이 돌 때까지 `waypoints/.tmp/`(git에 안 올라가는 로컬 전용 폴더)에만 있었기 때문입니다. 원격 웹 세션은 매번 새 컨테이너로 시작하고 끝나면 컨테이너째 회수되는데, Archive가 `SessionEnd` 완료를 컨테이너 회수 전에 보장한다는 근거가 없어서 — 그 경우 로컬에만 있던 원문이 그대로 사라졌습니다.

**수정 내용** (요청하신 대로 "로컬 임시저장 → 세션 종료 시 정리"라는 계약은 유지하되, 매 턴 커밋 방식으로 durability 문제를 해결):
- `Stop` 훅이 매 턴 대화를 `waypoints/inprogress/<프로젝트>/<세션ID>.md`(git-tracked)에 append하고 바로 `git commit+push`합니다. 커밋 메시지는 `waypoint-log: ...`로 명확히 구분해서, 이게 AI 분류 전 원문 누적 로그라는 걸 한눈에 알 수 있게 했습니다.
- `SessionEnd`는 그대로 이 원문을 분류해서 `waypoints/tags/`로 정리하고 원문 로그를 삭제하는, 최종 정리(`waypoint: ...`) 역할만 담당합니다.

## 1) "찾은 문서를 다 읽어야 하는가" — 아니요, 여기도 단계적으로 갑니다

`Grep`은 파일 전체를 돌려주지 않고 **매칭된 줄 + 주변 맥락(`-C` 옵션)만** 돌려줍니다. 그러니 검색 자체(후보 추리기)는 비용이 거의 없고, 진짜 비용은 "그 후보들을 몇 개나 전체로 열어보느냐"에서 나옵니다.

지금 `SKILL.md`에 이미 있는 원칙 — "전부 다 읽지 말고 관련 있어 보이는 것만, 최신순으로 우선" — 을 grep 결과에도 그대로 적용하면 됩니다:
1. Grep으로 후보 목록 + 스니펫만 확보 (싸다)
2. 제목·타임스탬프·스니펫만 보고 진짜 관련 있어 보이는 몇 개만 추림
3. 그 몇 개만 전체로 열어서 정확히 확인

즉 "검색된 게 10개면 10개 다 열어본다"가 아니라 "10개 중 스니펫으로 봐서 진짜 관련 있는 2~3개만 연다"는 절차를 grep 기반 검색에도 명시해두면 됩니다.

## 2) "한 세션이 길면 그 문서 하나가 커서 비싸지지 않나" — 이건 실제로 다른, 더 중요한 문제를 하나 찾았습니다

`waypoints/tags/`에 저장되는 건 원본 대화가 아니라 **AI가 압축한 요약**(`summary_md`)이라서, 세션이 길었어도 그 요약 파일 자체는 짧습니다 — 여기까진 문제없습니다.

그런데 코드를 다시 보니:
```python

```
**분류할 때 원문의 첫 20,000자만 AI에게 넘깁니다.** 세션이 그보다 길면(지금 이 대화도 이미 그정도는 넘었을 겁니다), **뒷부분 내용은 요약에 아예 안 들어갈 수 있습니다.** 원문 자체는 이미 `inprogress/`에 매 턴 커밋돼서 git 히스토리엔 남아있지만(안전), 정리 과정에서 `inprogress` 파일은 삭제되고 tags/의 요약본만 남기 때문에 — 나중에 grep으로 검색해도 **뒷부분 내용은 요약본에 없어서 못 찾을 수 있습니다.** 이건 검색 방식(grep이냐 인덱스냐)과 무관하게, **저장(요약) 시점에 이미 정보가 누락되는** 문제라 더 근본적입니다.

## 근본 해결: 청크 단위 맵-리듀스 요약

긴 문서를 요약할 때 쓰는 표준 기법입니다 — 길이 제한이 있는 게 아니라, **애초에 한 번에 다 읽지 않는** 구조로 바꾸는 겁니다.

1. **분할(Map)**: 원문을 턴 경계(`### [HH:MM:SS] 사용자/Claude`) 기준으로 예를 들어 15,000자 안팎 청크로 나눔
2. **각 청크를 개별적으로 요약**: 청크마다 `claude -p`를 호출해서 "이 부분의 핵심 결정/이유만 짧게 요약" — 원문 15,000자 → 요약 몇 백 자로 압축
3. **압축된 요약들만 모아서 최종 분류(Reduce)**: 지금 있는 `CLASSIFY_INSTRUCTIONS` 호출에 원문 대신 **청크 요약들을 이어붙인 것**을 넣음 — 세션이 아무리 길어도 이 최종 입력은 청크 개수 × 짧은 요약이라 계속 작게 유지됨
4. 짧은 세션(청크 1개 이하)은 지금처럼 그냥 바로 분류 — **추가 비용 없음, 긴 세션에서만 발동**

이게 "제한을 올리는 것"과 다른 이유: 20,000자를 20만자로 올려도 그보다 긴 세션은 또 나오지만, 맵-리듀스는 세션이 아무리 길어도 최종 호출 크기가 "청크 개수"에만 비례해서 커지고 그 개수 자체도 계속 압축해나갈 수 있어서(필요하면 요약의 요약도 가능) 상한이 사실상 없습니다.

**트레이드오프**: 긴 세션일수록 `claude -p` 호출이 여러 번 필요해서 시간이 더 걸립니다. 순차 호출하면 지금 `SessionEnd` 훅 타임아웃(55초)을 넘길 수 있으니, 청크들을 **병렬로 호출**하고 훅 타임아웃도 조금 올려야 할 것 같습니다.
